# fromlog 운영·장애 복구

2026-09-27 기준. 실제 구성의 정본은 `docker-compose.yml`, `/docker/backup/*.sh`, 프로젝트 비공개 환경 파일이다.

## 상태 확인

- `GET /api/health`: 프로세스 응답 여부(200). DB가 정상이라는 뜻은 아니다.
- `GET /api/ready`: DB/Redis/검색 서버에 가벼운 검사를 수행한다. 전부 정상 200, 일부 실패 503. 내부 주소·자격증명·오류 원문은 노출하지 않는다. 검사 요청은 병합하고 5초간 결과를 재사용한다.
- 관리자 봇 목록/활동 로그: 수집 상태·최초 실패·자동 정지·푸시 재시도 완료 확인.
- `bot_ops_alerts`: 자동 정지 알림 발송 대기. `bot_id`, `attempts`, `next_attempt_at`으로 재시도 여부를 확인한다. payload에는 오류 정보가 있어 비공개로 취급한다.
- Docker 로그: DB 활동 로그 기록이 실패해도 코드·행위자·분류를 남긴다. Compose의 local 로그 회전은 서비스당 10MB × 3파일이다.

```bash
docker compose ps
docker compose logs --since 15m fromlog-backend
```

조회 실패를 곧바로 봇 설정 문제로 판단하지 않는다. `ready`로 DB/Redis/검색 상태를 확인하고 Nitter/외부 API 응답을 구분한다. Redis 장애 동안 DB 기반 공개 조회는 캐시 없이 동작하지만 Redis를 직접 사용하는 모든 부가 기능까지 정상임을 보장하지 않는다.

## 봇과 알림

- 수집 작업은 프로세스 내 중복 실행 방지와 DB 자원 잠금으로 보호한다. 현재 백엔드 **1개 인스턴스** 구성을 기준으로 한다. 여러 인스턴스 수평 확장 검증은 하지 않았다.
- 연속 10회 오류 시 기존 자동 정지 정책을 유지한다. API 쿼터 오류를 성공/빈 결과로 처리하지 않는다. Gemini/YouTube 오류 안내를 구분한다.
- 자동 정지는 알림 전송보다 먼저 처리한다. 알림은 DB에 넣고 즉시 발송을 시도하며 실패/부분 성공/수신 기기 없음은 대기 상태로 남긴다.
- 대기열은 매분 검사하고 1분부터 최대 1시간까지 간격을 늘린다. 프로세스 재시작 후에도 남는다. 수동으로 봇을 다시 시작하면 과거 대기 알림을 취소한다.
- 전달은 최소 한 번을 지향한다. 부분 성공 또는 전송 직후 종료 시 중복 푸시가 가능하며 이미 진행 중인 전송을 취소할 수는 없다. DB 자체가 끊겨 대기열 기록에 실패한 경우 서버 로그로 확인한다.
- Redis 상태 저장 실패는 프로세스 메모리에 임시 보관하고 연결 회복 시 반영한다. Redis와 백엔드가 동시에 중단되면 그 임시 상태는 잃을 수 있다. 수집 원본·체크포인트·enabled는 DB에 보관한다.
- 활동 로그 3,224건을 확인했다. DB 기록을 임의로 삭제하는 보관 정책은 도입하지 않았다. 용량 증가와 필요한 보관 기간에 따라 별도 정리한다.

## 백업·복구

| 대상 | 현행 경로/정책 | 복구 방식 |
| --- | --- | --- |
| DB | `/docker/backup/db/`, 매일 03:30 KST, 로컬 7일 | gzip 덤프를 같은 DB 버전의 격리 인스턴스에 먼저 복원 |
| 서버 파일·비공개 설정·RustFS | `/backup/restic`, 매일 04:00 KST | 선택한 스냅샷을 별도 디렉터리에 복원 후 확인 |
| 추가 복제 | 메인 PC가 온라인이면 5분 타이머로 새 스냅샷 복제 | 메인 PC 보관본은 이번에 접속/복구하지 않음 |
| 검색 색인 | DB에서 재생성 가능 | 복원 DB 검증 후 관리자 검색 동기화 |
| Redis | 캐시 및 운영 상태 | 임시 캐시는 다시 생성, 수집 원본은 DB 기준 |

2026-09-27 덤프는 MariaDB **12.1.2**에서 생성했다. 11.x에 그대로 넣으면 외래키 이름 중복으로 실패할 수 있으므로 버전을 맞춘다. 전체 덤프에서 fromlog만 추출할 때는 `backend/test/fixtures/extract-fromlog-backup.py`를 사용해 덤프 헤더의 복원 설정도 유지한다.

복구 순서:

1. 적용 전 현재 DB·미디어·비공개 환경 파일과 배포 커밋/이미지 식별자를 따로 보존한다.
2. restic의 선택 스냅샷을 **별도 경로**로 복원한다. 기존 `/docker`에 직접 덮어쓰지 않는다. 저장소를 읽기 전용으로 마운트한 검사에서는 `--no-lock`으로 읽었다.
3. 운영과 같은 MariaDB 버전을 외부 네트워크 없이 실행하고 fromlog 덤프만 주입한다. 봇 스케줄러/외부 API 키를 연결하지 않는다.
4. 테이블 검사, 건수, 외래키 관계, 공개 API를 확인한다. [자동 복원 검사](../backend/test/OPERATIONS.md)를 따른다.
5. RustFS 데이터는 객체의 메타데이터/버전 디렉터리를 포함해 복원한다. 단순히 공개 파일 이름만 복사하지 않는다. 표본 파일 해시가 같아도 전체 스토리지의 일관성을 보장하는 것은 아니다.
6. 실제 전환 시 봇을 멈추고 DB/파일을 같은 복구 지점으로 전환한다. `.env`·Firebase 계정 파일·Nitter 세션·Kiwi 모델·앱 서명키도 별도 확인한다. `node_modules`, `dist`, `.git`은 restic 제외 대상이므로 잠금 파일 기반 의존성 설치와 Git 이력이 필요하다.
7. 검색 색인을 DB에서 재생성하고 건강 상태/공개 조회를 확인한 뒤 필요한 봇만 재개한다. Redis의 과거 상태 표시만으로 수집 완료를 판단하지 않는다.

## 배포·종료·롤백

- 이번 변경은 먼저 `backend/sql/20260927-ops-alerts.sql`을 적용한다. additive 테이블이며 기존 행을 바꾸지 않는다.
- 백엔드는 개발·운영 공용 bind mount + watch이다. 소스 편집 자체가 공용 서버 재시작과 정상 봇 시작 폴링을 유발한다. 운영 데이터를 사용하는 장애 주입은 하지 않는다.
- 다음 승인된 백엔드 재생성부터 `init: true`, 종료 유예 25초, `/api/ready` healthcheck, 고정 의존성 설치(`npm ci`), 로그 회전이 적용된다. healthcheck의 unhealthy만으로 Docker가 자동 재시작하지는 않는다.
- 종료 신호는 `app.close()`로 보내 cron/집중 폴링을 멈춘다. 실행 중 수집은 최대 8초 기다리고 전체 종료는 20초로 제한한다. 장기 작업이 잘리면 앞선 검증의 DB 체크포인트/중복 방지로 재개한다. Docker의 다음 재생성 전에는 기존 프로세스 실행 래퍼가 남아 있다.
- 승인된 재생성 명령: `docker compose up -d --build fromlog-backend`. 프론트 배포는 별도 `fromlog-frontend-prod` 서비스로 한정한다. 전체 compose를 무조건 재시작하지 않는다.
- 배포 전 정상 이미지와 커밋을 기록한다. 프론트는 이전 정적 이미지로 복구할 수 있다. **백엔드는 이미지 교체만으로 bind mount 소스가 되돌아가지 않는다.** 현재 작업을 보존한 뒤 해당 변경의 revert 또는 별도 검증된 체크아웃을 사용한다.
- 코드 롤백 시 `bot_ops_alerts`는 먼저 유지한다. pending 알림을 확인하기 전에 DROP하지 않는다. 이전 코드에서는 대기열이 처리되지 않으므로 새 버전 복귀 후 재시도하거나 운영자가 처리한다.

운영 DB 덮어쓰기·전체 미디어 교체·전체 서버 재시작·이전 버전의 실제 운영 전환은 이 검증에서 수행하지 않았다.
