## 발견 문제와 수정

1. **파싱 실패 글 영구 제외**: 기존에는 파싱 오류를 crawl log에 저장한 뒤 성공처럼 반환했고, 상태와 관계없이 처리한 글로 판단했다. 이제 오류를 전파하며 성공한 처리만 건너뛴다. 기존 `error` 이력도 재시도 가능하다.
2. **부분 저장·AI 재호출·알림 누락**: 추출 결과를 `bot_collection_runs`에 먼저 저장하고 큐/누락 표시/처리 완료/알림 대기 플래그를 하나의 트랜잭션으로 반영한다. 재시작 시 미완료 결과부터 처리한다.
3. **알림 실패가 사라짐**: 발송 대기 상태를 DB에 남기고 다음 수집 때 재시도한다. 부분 실패·발송 건너뜀도 실패로 기록한다.
4. **AI의 중복 오판으로 일정 소실**: 코드가 중복으로 확인하지 못한 AI 중복 판단은 검토용 `dup_hint`로 남긴다.
5. **응답 검증·스크래핑 문제**: Gemini 필드 타입/범위/응답 종료 상태, DC 본문 영역·목록·중첩 태그를 검증한다. DC 화면 설정 문구를 제목으로 읽던 문제를 게시글 제목/OG 메타데이터로 수정했다. 본문 수신까지 타임아웃을 유지한다.
6. **같은 글의 수정 미반영·오래된 대기 정보**: 신규 수집부터 URL+본문 해시로 실행을 구분한다. 내용이 바뀌면 미등록 대기 항목의 시간·부가 정보를 갱신한다. 긴 제목은 키 일부를 해시로 바꿔 DB 길이 초과를 막는다.
7. **재시작과 정지 상태 불일치**: 서버 재시작 시 오류 누적을 유지하고, 집중 수집 시간대의 남은 구간을 재개한다. 이전 실행/이전 폴링 세션의 늦은 결과를 무시한다. 최근 추가 0건과 소요시간도 갱신한다.
8. **검색 반영 실패를 등록 성공으로 표시**: 등록 API가 검색 반영 실패를 503으로 알려 같은 ID로 재시도하도록 했다. PC/모바일의 기존 오류 처리에서 편집창을 유지하는 것을 소스로 확인했다.

## 재검증 근거

- 기존 수집 중복/스케줄러/큐 등록 기준 테스트 34개 통과 후 장애 시나리오를 추가했다.
- 저장소 코드로 **111개 테스트 노드 통과** 후, 시작 시 성공했는데 이전 오류 문구가 남는 경우를 추가 보정하고 스케줄러 **11개를 재검증**했다(고유 테스트 총 112개). 유튜브/X 회귀, 일정 수집 통합, 큐 등록, 스케줄러 및 추출 검사를 포함한다.
- 새 통합 검사는 운영 자격증명을 받지 않으며 loopback의 `collection_audit_*` DB를 생성/제거한다. 강제 종료 테스트도 이 격리 DB 안에서만 실행했다.
- 실제 FCM 발송·Gemini 요청·큐 수동 등록/무시·수동 봇 동기화는 실행하지 않았다. DC 공개 HTML 읽기만 별도로 수행했다.
- `git diff --check`, 공용 백엔드 재시작 후 health/봇 상태, 기존 큐 건수 확인. 프론트/앱 변경 없음.

### 재현 실행

외부 네트워크 없는 별도 MariaDB 11(root 빈 비밀번호)을 준비한다. 테스트 컨테이너는 그 DB의 network namespace를 공유하며 운영 환경변수/자격증명을 넘기지 않는다.

- DB에 `fromlog_test_pending`을 생성한다. 수집/봇 통합 DB는 테스트가 생성한다.
- 단위/큐: `JWT_SECRET=test PENDING_TEST_HOST=127.0.0.1 npm run test:collection`
- 수집 통합: `JWT_SECRET=test COLLECTION_AUDIT_DB=1 npm run test:collection:integration`
- 유튜브/X 회귀: `JWT_SECRET=test npm run test:bots`
- 유튜브/X 통합: `JWT_SECRET=test BOT_AUDIT_DB=1 npm run test:bots:integration`
- FCM은 함수 대역, 외부 HTTP/S3/검색은 모의 응답을 사용한다. 테스트 컨테이너에는 `FIREBASE_SERVICE_ACCOUNT=/nonexistent`도 지정한다.

## 스키마·운영 반영

- `backend/sql/20260926-collection-recovery.sql`의 추가 테이블을 먼저 적용했다. 기존 테이블/행은 변경하지 않는다.
- 검증한 코드를 공용 백엔드에 반영했다. 제목 추출의 모바일 HTML 차이와 시작 시 오류 문구 초기화를 추가 보정해 watch 재시작이 총 3회 발생했다. 정상 봇의 시작 폴링은 기존 정책대로 실행됐다.
- 기존 큐: 대기 4건, 등록 18건(연결 18건), 무시 20건. 수동 변경 없음.
- 최신 원문은 기존 성공 이력이 있어 재시작 수집에서 Gemini를 호출하지 않고 0건으로 완료했다.
- 프론트 운영 빌드·Git push는 하지 않았다. 임시 DB/테스트 컨테이너는 제거했다.
- 롤백 시 이번 백엔드 코드 변경을 되돌리고 새 테이블은 우선 유지한다. 실행 이력/발송 대기 데이터를 확인하기 전 DROP하지 않는다. 기존 코드도 추가 테이블이 있어 동작한다.

## 한계 및 후속 확인

- 추출 정확도 자체는 모델/원문에 의존한다. 이번에는 무료 한도를 사용하지 않았으므로 실제 Gemini 출력 품질을 다시 평가한 검사는 아니다.
- AI 응답 수신과 추출 결과 저장 사이에서 죽으면 해당 호출은 다시 필요할 수 있다. **저장된 추출 결과가 있는 이후 단계**의 복구에서 추가 호출을 막는다.
- 도입 전 이미 성공한 글은 과거 성공 이력을 존중해 다시 추출하지 않는다. 해당 글의 이후 수정까지 소급 감지하지 않는다.
- 기존 큐 식별 규칙(날짜+정규화 제목)은 유지한다. 같은 날짜·같은 제목으로 여러 회차가 있으면 원문의 회차 구분이 필요하다. 날짜 정정으로 다른 키가 생기면 예전 항목은 누락 표시와 수동 검토 대상이다.
- 푸시는 최소 한 번 발송을 지향한다. 일부 기기만 성공했거나 발송 직후 DB 갱신 전에 중단되면 알림이 중복될 수 있다. 기기별 수신 완료/정확히 한 번 전달을 보장하지 않는다. 실제 휴대폰 수신/딥링크는 10번에서 검증한다.
- 연속 10회 실패 자동 정지는 기존 정책이다. 수집 또는 푸시 장애가 계속되면 원인 해결 후 관리자가 다시 시작해야 한다. 자동 정지 알림 자체의 장애 재발송·Redis 장애·전체 백업 복원·장기 보존 정책은 12번 범위다.
- 검색만 실패한 큐는 DB 등록이 끝난 상태다. 열린 창에서 재시도할 수 있고, 창을 닫았다면 기존 자정 전체 검색 동기화 또는 관리자 동기화로 복구한다.
- 정지는 진행 중 외부 요청/이미 시작된 저장을 취소하지 않는다. 상태 반영과 다음 실행을 제어한다.
