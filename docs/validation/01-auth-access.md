웹 관리자는 비밀번호 또는 허용된 Google 계정으로 JWT를 발급받는다. PC·모바일은 같은 인증 API와 저장소를 사용한다. 앱에는 별도 사용자/관리자 로그인 화면이 없으며 공개 API를 사용하므로 관리자 로그인 검사는 해당하지 않는다.

JWT 보호 API 102개의 인증 훅을 확인했다. 공개 쓰기 API(로그인, 일정 제안 저장, 푸시 등록/해제)와 별도 키로 보호되는 Nitter 세션 갱신·운영 푸시 API는 JWT 보호 대상과 구분했다. 공개 입력·푸시 등록 정책 및 앱의 운영 푸시 등록용 키는 7번/10번에서 추가 검증한다.

## 발견한 문제와 수정

| 문제 | 수정 결과 |
| --- | --- |
| JWT 서명만 유효하면 삭제된 관리자 계정의 토큰도 통과 | 매 인증 요청에서 관리자 ID·사용자명·필수 claim 확인 |
| 로그아웃이 브라우저 저장소만 비워 기존 토큰을 다시 사용할 수 있음 | 서버에 토큰 SHA-256 해시를 만료 시각까지 보관하고 재사용 차단 |
| 같은 초의 로그인에서 동일 토큰이 발급될 수 있음 | 각 로그인에 고유 jti를 넣어 다른 기기 세션과 구분 |
| 저장된 로그인 상태로 인증 확인 전에 관리 화면이 표시될 수 있음 | 서버 검증 성공 후 보호 화면 표시 |
| 인증 실패·계정 전환 후 캐시와 세션 처리가 일관되지 않음 | 보호 API 401 시 해당 세션만 해제, 토큰 변경 시 쿼리 취소·캐시 초기화, 다른 탭에도 반영 |
| 일시적 서버/통신 오류를 만료처럼 취급하거나 확인 화면에 머무름 | 503/통신 실패는 세션 유지, 재시도 화면 제공 |
| 로그아웃 서버 요청 실패에 대한 처리 없음 | 실패 시 로그인 상태 유지 및 오류 표시·재시도 |
| 저장된 만료 토큰 확인 중 Google 버튼이 렌더링되지 않을 수 있음 | 인증 확인 종료 후 Google 버튼 초기화 |

기존 JWT 유효기간은 변경하지 않았다. jti가 없는 기존 토큰도 검증·로그아웃할 수 있다. 새로 발급되는 토큰은 로그인마다 다르며 한 세션의 로그아웃이 다른 세션을 해제하지 않는다.

## 검증 근거

### API 자동 테스트

`docker exec fromlog-backend npm run test:auth`: **9/9 통과**.

- 토큰 없음·잘못된 서명·만료·필수 claim 누락·없는 관리자·사용자명 불일치 차단
- 비밀번호 성공/실패, 로그인 시도 제한, Google audience·인증된 이메일·허용 목록 검사
- 로그아웃 토큰 재사용 차단, 다른 세션 보존, 같은 초 로그인 구분
- 인증 저장소 장애 시 503으로 접근 차단
- 102개 보호 라우트 각각 토큰 없음/잘못된 토큰으로 요청하여 핸들러 실행 전 차단
- 별도 키가 필요한 Nitter 조회/운영 푸시 요청에서 키 누락 차단

테스트 파일: `backend/test/auth-access.test.js`, `backend/test/auth-routes.test.js`.
라우트 전수 테스트는 입력 스키마를 테스트 내에서 제거하고 실제 인증 preHandler를 실행한다. 잘못된 body의 400 응답과 인증 훅 검사를 분리하기 위한 것으로, 모든 입력 조합의 검증을 의미하지 않는다. DB·Google 검증기는 대역을 사용하며 실제 수집·발송·삭제 핸들러는 실행하지 않는다.

### 실제 API·DB 확인

- 개발 API `/auth/verify`, `/admin/bots`, `/admin/pending/count`, `/stats`, `/admin/nitter/session`에 인증 없이 접근하여 모두 401 확인.
- 실제 MariaDB 트랜잭션 안에서 테스트 전용 서명키로 검증 성공 → 로그아웃 → 토큰 재사용 401을 확인하고 롤백했다. 기존 사용자 세션과 데이터는 변경하지 않았다.

### PC·모바일 브라우저

개발 사이트 Chromium 1440px·390px, 모의 API 응답으로 다음을 각각 확인했다.

- 비로그인 상태에서 홈·일정·큐·일정 추가/수정·영상·봇·테마·로그·앨범·멤버 등 11개 관리자 경로 직접 진입 차단
- 인증 확인 전에 보호 데이터 요청을 보내지 않음
- 잘못된 비밀번호, 로그인, 새로고침, 만료 토큰 해제
- 로그아웃 실패 후 재시도, 다른 세션으로 재로그인 시 새 토큰 검증
- 인증 확인 일시 실패 시 세션 보존 및 재시도 복구
- 보호 API 401 수신 시 로그인 화면으로 복귀
- 별도 시나리오: 만료 토큰 확인 후 Google 버튼 표시·모의 로그인, 다른 탭으로 로그아웃 전파
- 브라우저 실행 오류 없음. 인증 실패 재시도 화면과 PC·모바일 관리자 화면 캡처 확인.

프론트엔드 `npm run build` 통과. 기존 큰 번들 크기 경고는 13번 성능 검증 대상이다.

### 수정 필요: 로그아웃 토큰의 동등한 표기 재사용 (중간 위험도)

`backend/src/utils/authSession.js:3`은 토큰 원문을 해시하지만 서명 검증은 다른 표기도 동일한 서명 바이트로 해석한다. 이미 확보한 미만료 관리자 토큰은 로그아웃 이후 표기를 바꿔 폐기 조회를 피할 수 있다. 새로운 토큰을 위조하거나 서명키 없이 임의 계정으로 로그인하는 문제는 아니다.

- 재현: 원본/동등 표기 모두 로그아웃 전 200 → 로그아웃 200 → 원본 401, 동등 표기 200.
- 테스트 전용 서명키·메모리 DB를 사용했으며 운영 토큰/DB를 사용하지 않았다.
- 수정 방향: 검증된 세션 ID 기준 폐기 또는 엄격한 정규형 토큰 검증. 기존 폐기 기록과 jti 없는 토큰의 호환 정책도 필요하다.
- 회귀 검증: 원본 및 동등한 표기를 모두 차단하고 다른 로그인 세션은 유지해야 한다.

### 수정 필요: 프록시 뒤 사용자들이 로그인 제한을 공유 (중간 위험도)

`backend/src/app.js:30`의 기본 Fastify 설정은 프록시 신뢰를 설정하지 않아 `request.ip`가 실제 사용자 대신 프록시 주소가 된다. `backend/src/routes/auth.js:26`의 제한이 같은 프론트엔드를 쓰는 모든 사용자에게 적용되어, 비로그인 사용자가 제한을 소진하면 다른 관리자도 신규 로그인이 막힌다. 초과 요청은 차단 시간을 연장한다.

- 재현: 같은 프록시 소켓, 다른 전달 IP를 가진 테스트 요청에서 첫 사용자의 실패 5회 후 다른 사용자가 429를 받았다.
- 기존 JWT 세션은 영향을 받지 않으며 공격 요청이 멈추고 제한 시간이 지나면 복구된다.
- 수정 방향: 신뢰할 프록시 경로/주소와 전달 IP 정규화를 함께 정의한다. 임의 `X-Forwarded-For`를 무조건 신뢰하는 방식은 피한다.
- 회귀 검증: 서로 다른 사용자 제한 분리, 위조 전달 헤더 차단, 비밀번호·Google 두 경로 확인.
