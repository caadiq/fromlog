# 일정 검색 비교: Meilisearch와 OpenSearch + Nori

**검증일: 2026-10-15 · 운영 검색 교체 없음 · 비교 완료**

## 결론

**한국어 조사·복합 검색의 개선 가능성은 OpenSearch + Nori가 더 컸다. 현재 사이트에 바로 적용할 종합 선택으로는 Meilisearch를 먼저 개선하는 편을 권장한다.**

Nori에 고유명사·부분 일치·별칭을 보완한 후보가 이번 검색 품질 점수에서 가장 높았다. 그러나 기본 Nori만 적용하면 현재보다 나빠졌고, 개선 후보도 일부 오타와 최신 일정의 순서가 퇴보했다. 메모리와 운영 복잡성도 늘어난다. 따라서 **Nori 설치 자체가 해결책은 아니며, 검색 데이터·질의·정렬을 함께 설계해야 한다.**

- 기존 일정 포스터 재사용 기능은 [운영 배포 완료](../deployments/2026-10-15.md).
- 운영 웹·앱·봇은 계속 기존 Meilisearch를 사용한다. 이번 비교를 위해 운영 검색 설정이나 문서를 수정하지 않았다.
- OpenSearch/Nori와 비교용 Meilisearch는 별도 내부 Docker 네트워크에 설치했다. 공개 포트·도메인·운영 API 연결 없음. 비교용 데이터는 정적 스냅샷이며 자동 동기화하지 않는다.
- [재현·관리 방법](../../tools/search-lab/README.md), [수치 및 검색별 결과 JSON](search-comparison-2026-10-15.json).

현재 기준은 운영 인덱스의 문서와 설정을 복제하고 기존 검색어 확장·학교명 검색·점수 기준·병합·날짜 보조 정렬을 재현했다. 실제 공개 검색 API에 반복 요청하여 검색어 학습 기록을 쓰지 않았다. DB 상세 재조회, 웹 서버, 브라우저 렌더링 시간은 성능 수치에 포함하지 않는다.

### 비교 후보

1. **현재 Meilisearch**: 현행 데이터·설정·질의 흐름 복제.
2. **Meili 데이터 보완**: 설명/방송사/학교명 및 Unicode 정규화만 보완. 현행 질의 흐름 유지.
3. **Meili 개선 후보**: 위 데이터 + 별칭, 숫자 오타 금지, 모든 단어 일치와 결과 없음 재시도, 기존 학교명 확장, 서버 필터·페이지 크기 제한.
4. **기본 Nori**: 현행 데이터 + Nori 분석/AND 검색. 별칭·고유명사·오타 보완 없음.
5. **OpenSearch standard 개선 후보**: 보완 데이터 + 별칭·학교명 확장, 필드/문구 가중치·부분 일치·오타/영문 자판 재시도.
6. **OpenSearch Nori 개선 후보**: 5번과 같되 주 분석기를 Nori로 설정. 고유명사 보존용 standard 보조 필드 사용.

두 개선 후보에는 같은 약칭을 적용했다. Nori와 standard를 별도로 비교하여 데이터 보완·별칭 효과를 모두 Nori 효과로 잘못 해석하지 않도록 했다. 실험 설정은 운영 코드에 적용하지 않았다.

## 검색 품질

| 후보 | 상위 10개 순위 점수¹ | 정답 회수율² | 상위 5개 내 정답 존재 | 정답 없는 검색 처리 |
| --- | ---: | ---: | ---: | ---: |
| 현재 Meilisearch | 86.2 | 68.0% | 54/58 | 3/4 |
| Meili 데이터 보완 | 86.2 | 80.0% | 55/58 | 2/4 |
| Meili 개선 후보 | 88.7 | 83.2% | 56/58 | 4/4 |
| 기본 Nori | 71.3 | 58.2% | 43/58 | 4/4 |
| OpenSearch standard 개선 후보 | 91.1 | 80.9% | 56/58 | 4/4 |
| OpenSearch Nori 개선 후보 | **94.6** | **90.1%** | **58/58** | 4/4 |

¹ nDCG@10 × 100: 명시적 키워드 규칙에 따라 제목 일치 3점/출처 포함 2점/설명 포함 1점으로 채점한 상대 비교다. 사용자 만족도나 정확도 백분율이 아니다. **최신성은 이 점수에 반영하지 않았다.**

² 검색어별 규칙상 정답 중 회수한 비율의 평균. 상위 5개에 정답이 존재한다는 것은 결과 전체가 정확하다는 뜻이 아니다.

### 실제 차이

| 검색 | 관찰 | 해석 |
| --- | --- | --- |
| `건대` | 현재는 건국대 일정을 놓치고 군대 관련 결과. Meili 개선은 건국대가 1위지만 잡음이 남음. Nori 개선은 건국대 1건 | 기본 Nori는 0건이었다. 약칭 사전과 질의 방식의 효과가 크다 |
| `박지원이` | 현재 6건, Nori 개선 277건 | 조사 처리 개선. 성 없이 `지원`만 있는 문서는 정답 규칙에서 빠질 수 있어 모든 현재 결과를 오답으로 볼 수는 없음 |
| `JTBC` | 현재 5건 → 두 개선 후보 9건 | 방송사 필드 색인 보완의 효과 |
| `박지원 불참` | 현재 1건 → 두 개선 후보 8건 | 설명 색인 보완의 효과 |
| `서울대학교 POLARIS` | 현재 7건 → 두 개선 후보 0건 | 현행 방식은 단어 일부를 포기하며 관계없는 결과가 나올 수 있음 |
| `프로미스나잉` | Meili는 다수의 관련 제목 검색. Nori 개선은 출처에만 관련 이름이 있는 1건 | **Nori 후보의 약점.** 약한 결과 1건 때문에 '0건이면 오타 재시도'가 작동하지 않음 |
| `워크돌 박지원` | 두 개선 후보 모두 일부 결과의 순위가 나빠짐 | `지원`/`박지원`과 출연 멤버를 연결하는 데이터가 필요. 어느 엔진도 인물 관계를 자동으로 보장하지 않음 |

고유명사를 Nori 사전에 단순히 추가하는 실험도 했으나 조사 분리가 항상 개선되지는 않았다. 최종 후보는 고유명사 보조 필드와 부분 일치를 사용했다. `이채영의` 같은 이름+조사의 회수도 여전히 불완전하다.

### 최신 일정 우선순위

규칙상 관련 일정 중 날짜가 가장 늦은 항목이 상위 10개에서 몇 번째인지 별도 확인했다. 이것은 '모든 검색은 최신순이어야 한다'는 뜻이 아니라, 프로그램명으로 다음 일정을 찾는 사용 흐름을 점검한 것이다.

| 검색 | 최신 날짜 | 현재 Meili | Meili 개선 | Nori 개선 |
| --- | --- | ---: | ---: | ---: |
| 계약결혼 | 10/17 | 1위 | 1위 | 1위 |
| 아는형님 | 10/03 | 3위 | 3위 | 3위 |
| 워크돌 | 10/21 | 1위 | 1위 | 1위 |
| 방판소녀들 | 10/15 | **1위** | **1위** | **8위** |
| 헬스키친 | 10/23 | 3위 | 3위 | 1위 |

Nori 개선의 `방판소녀들` 1위는 6월의 X 게시물이었다. 문구 빈도·문서 길이 등의 관련도 점수가 날짜 보조 정렬보다 먼저 작동한다. **검색 품질 점수만 보고 교체하면 실제 일정 찾기는 나빠질 수 있다.** 프로그램명 정확 일치와 예정/최신 일정의 우선순위를 별도로 검증해야 한다.

## 속도

### 검색 처리 흐름 전체를 흉내 낸 실험

| 후보 | 중앙값 | 95% 요청 완료 시간 |
| --- | ---: | ---: |
| 현재 Meili 흐름 | 5.00ms | 27.25ms |
| Meili 개선 | 3.19ms | 7.72ms |
| Nori 개선 | 2.91ms | 5.57ms |

현재 흐름은 최대 10,000건과 전체 속성을 받고 병합한다. 개선 후보는 성능 측정에서 필요한 20건을 받는다. 따라서 이 차이는 **엔진 차이뿐 아니라 요청량·질의 흐름 변경의 효과**다. 품질 평가에서는 전체 결과를 조회했다.

같은 서버에서 4개 동시 요청을 보낸 결과는 현재 Meili p95 66.0ms, Meili 개선 41.2ms, Nori 개선 51.5ms였다. Nori가 모든 부하 조건에서 더 빠르지는 않았다. 이 규모의 짧은 테스트로 최대 수용량을 판단하지 않는다.

### 엔진에 같은 크기의 요청을 보낸 대조 실험

동일한 기존 문서에서 1회 검색 요청으로 ID 20개만 받았다. 질의 분석 방식까지 같다는 뜻은 아니며, 결과 회수량 차이를 제거한 대조군이다.

| 엔진 | 중앙값 | 95% 요청 완료 시간 |
| --- | ---: | ---: |
| Meilisearch | **2.22ms** | **4.12ms** |
| OpenSearch Nori | 3.61ms | 4.99ms |

둘 다 현재 데이터 규모에서는 충분히 빨랐다. **속도만을 이유로 교체할 근거는 없었다.** 현행 서비스에는 모든 검색 ID를 DB에서 상세 조회한 후 페이지를 자르는 경로도 있어, 요청량·페이지 처리를 개선할 여지가 있다. 실제 페이지 체감 개선폭은 별도 API/UI 검증이 필요하다.

## 운영 비용과 기능

| 항목 | 비교용 Meilisearch | OpenSearch + Nori |
| --- | ---: | ---: |
| 재시작 후 예열된 메모리 표본 | 약 161MiB | 약 1.45GiB |
| 재시작 시작부터 조회 가능까지 | 0.43초 | 23.27초 |
| Docker 이미지 | 약 150MiB | 약 1.58GiB |
| 생성/수정/삭제 | 통과 | 통과 |
| 필터/정렬/페이지/강조 표시 | 통과 | 통과 |
| 재시작 후 변경 내용·문서 수 유지 | 통과 | 통과 |

각 엔진에 비교용 인덱스가 3개씩 있다. 메모리는 특정 시점의 표본이며 피크나 제품별 최소 요구량은 아니다. OpenSearch heap을 1GiB로 설정했고 기본 번들 플러그인이 포함돼 있다. 실제 운영 용량은 설정·캐시·사용 시간에 따라 달라진다. 재시작은 각 1회로 반복 통계가 아니다.

운영 전환 시 현재 Meili 전용 색인/재색인·봇 및 관리자 저장 동기화·실패 재시도·검색 점수 기준·자동완성 연동을 바꿔야 한다. Nori의 점수를 현재 Meili의 `0.5` 기준과 그대로 비교할 수 없다.

`워크`, `계약결` 접두어는 보완 후보에서 검색됐지만 `ㄱㅇㄱㅎ`, `ㅂㅈㅇ` 초성은 이번 후보 모두 결과가 없었다. 운영의 별도 추천/초성 서비스는 손대지 않았으며, Nori 설치가 해당 기능을 대신하지 않는다.

## 권장 후속 순서

1. **Meilisearch 유지 상태에서 설명·방송사 색인과 검색량/페이지 처리부터 개선.** 엔진 전환 없이 회수율과 비용을 개선할 수 있다. 데이터만 늘리면 관계없는 결과도 늘 수 있어 질의 조건을 함께 검증한다.
2. 학교/프로그램 약칭, 멤버 정규화, 프로그램명 정확 일치와 최신성 정책을 정리한다. 어느 엔진에도 필요한 작업이다.
3. 한국어 조사 검색 개선이 중요한지 실제 사용 사례를 더 모은다. Nori 후보의 약한 결과에서 오타 복구, 최신 일정 우선순위, 새 검색어에 대한 사람 평가를 완료한 후 전환을 결정한다.

위 개선은 **이번에 운영 적용한 변경이 아니라 다음 작업 제안**이다. 비교 환경은 설치 상태로 남겨 두었으며, 중지/재개 명령은 실험 README에 있다.

## 해석의 한계

- 정답은 명시적 키워드와 별칭을 이용한 규칙이다. 사람의 모든 의도·인물 관계를 평가하지 못한다. 예컨대 `콘서트` 규칙은 `개그콘서트`도 포함할 수 있다.
- 추가 17조건은 별도 표시했으나 기존 학교명 확장 누락을 수정하는 데 참고했으므로 완전한 블라인드 시험이 아니다. 후보 설정과 평가 집합이 독립적이라고 주장하지 않는다.
- 최신성·오타 사례를 별도로 보고 판단해야 하며 단일 평균 점수로 우열을 확정하지 않는다.
- 2,423건/단일 서버/단일 노드의 단기 실험이다. 대규모 확장성, 샤드 장애, 장기 안정성, 실사용 클릭 기반 A/B, OpenSearch를 연결한 웹·앱 UX는 검증하지 않았다.
- 운영 일정 내용 자체의 사실 여부나 날짜의 정확성을 검수한 작업은 아니다.
