# 13. 웹·앱 성능

- 검사일: 2026-09-27
- 상태: **보류 — 웹·Flutter 자동 검사/수정 완료, Android 실기기 성능 확인 대기**
- 시작 코드: `9882b7cb`.
- 다음 독립 작업: **14번 PC 공개 콘텐츠의 앨범·상세/뷰어 심화**. 10번과 이번 단계의 실기기 항목은 함께 확인한다.

## 범위와 방법

- Vite 배포용 빌드 전후를 로컬 gzip 서버에서 비교. PC 1440×900 / 모바일 390×844, 각 경로 3회, 새 브라우저 컨텍스트와 캐시 비활성화.
- PC: 지연 20ms, 다운로드 2MB/s. 모바일: 지연 100ms, 다운로드 200KB/s, CPU 4배 감속.
- 합성 API를 사용하며 외부 폰트/이미지는 차단한다. **아래 LCP는 실제 사이트 Core Web Vitals가 아니다.** 공통 환경의 전후 참고값이며, PC 일정처럼 지연 로딩/애니메이션의 타이밍에 따라 더 늦게 관측되는 항목도 있다.
- 실제 API는 읽기 요청만 경로별 3회. 운영 쓰기, 부하 공격, 봇/AI 강제 실행, 캐시 삭제 없음.
- 앱은 위젯 검사·정적 분석·Android arm64 릴리스 빌드. 연결된 Android 단말이 없어 GPU 프레임/발열/실제 WebView 메모리는 측정하지 못했다.

## 발견·수정

| 항목 | 재현/원인 | 변경/확인 |
| --- | --- | --- |
| 웹 첫 다운로드 과다 | 공개/관리자·PC/모바일 페이지를 모두 정적 import. 첫 JS gzip 약 393KB | 장치/관리자 라우트와 페이지를 필요할 때 불러온다. 최초 경로별 약 160~193KB. 청크 로드 실패는 재시도 안내와 새로고침으로 복구 |
| PC 홈 사진 10장 동시 요청 | 보이지 않는 슬라이드도 모두 img로 마운트 | 현재·이전 전환 사진·다음 사진만 유지. 최초 2장, 동작 줄이기는 1장. 11번 전환해 마지막→첫 사진 포함 정상 |
| 앱 같은 달 영상 전체 마운트 | 월 전체 Column/Wrap을 ListView의 한 항목으로 처리 | 월 헤더와 영상 줄을 각각 ListView 항목으로 분리. 600개 일반 영상: 마운트 600→4개, 쇼츠는 수정 후 3개. 스크롤 후에도 양쪽 30개 미만, 종료 예외 없음 |

앱의 위젯 객체·영상 데이터 자체가 4개로 줄어든다는 뜻은 아니다. **화면에 마운트되어 레이아웃·이미지 상태를 유지하는 카드 수**를 줄인 것이다. 일반 영상 2열/쇼츠 3열, 월 구분과 줄 등장 효과를 유지한다. 기존 페이지 추가 실패 검사는 가상화된 줄을 실제로 스크롤해 확인하도록 갱신했다.

## 첫 로딩 비교

라우트 분리 직후 측정. 단위는 gzip KB(1KB=1000bytes), 시간은 3회 중앙값. 홈 이미지 요청 최적화는 별도 검사했다.

| 화면 | 최초 JS 전→후 | 합성 LCP 전→후 |
| --- | --- | --- |
| PC 홈 | 393.1 → 176.8KB | 1.068 → 1.044초 |
| PC 영상 목록 | 393.1 → 181.2KB | 0.448 → 0.420초 |
| PC 일정 | 393.1 → 192.6KB | 0.424 → 0.940초 |
| 모바일 홈 | 393.1 → 160.3KB | 3.380 → 2.540초 |
| 모바일 영상 목록 | 393.1 → 167.8KB | 3.448 → 2.732초 |
| 모바일 일정 | 393.1 → 177.8KB | 2.656 → 1.180초 |

모바일 긴 작업의 50ms 초과분 합계 중앙값: 홈 222→64ms, 영상 108→29ms, 일정 220→82ms. 이 값은 Lighthouse TBT와 측정 구간이 달라 동일 지표로 취급하지 않는다. PC 모든 경로가 빨라졌다고 판정하지 않는다. 청크 요청이 추가되는 비용과 초기 전송량 감소의 교환 관계가 있다.

최종 빌드: 메인 JS 438.05KB / gzip 143.64KB. 나머지 경로별 청크까지 합한 것이 위 표의 첫 다운로드 크기다. 전체 사이트 코드 합계와도 구분한다.

## 대량 데이터·반복 이동

- 검색 2,000건: PC 실제 마운트 10→스크롤 후 15개, 모바일 12→17개. 긴 결과를 읽으면서도 DOM을 제한한다. 캡처 직접 확인.
- 웹 영상 600개: 24개씩 25페이지를 끝까지 스크롤. 중복 요청 없음, 위로 돌아와 채널 선택 가능, JS 예외 없음.
  - PC DOM 7,295개 / GC 후 JS 힙 약 17.55MB.
  - 모바일 DOM 7,286개 / GC 후 JS 힙 약 15.93MB.
  - 웹 영상은 가상 목록이 아니므로 DOM/데이터가 누적된다. 이번 600개 범위에서 기능은 정상이나 수천 개 연속 탐색·저사양 실기기의 프레임 유지를 보장하지 않는다. 실제 장기 사용에서 문제가 생기면 월/줄 가상화를 별도 적용한다.
- 일정↔영상 화면 20회 왕복 후 GC:
  - PC 5/10/20회 시 DOM 노드 678, 이벤트 314, 문서 1개로 유지. JS 힙 약 5.94→6.16→6.46MB.
  - 모바일 DOM 노드 674, 이벤트 240, 문서 1개로 유지. JS 힙 약 5.13→5.29→5.46MB.
  - 지속적인 DOM/리스너 누적이나 남은 iframe 없음. 이 짧은 검사를 장시간 메모리 누수 부재 증명으로 해석하지 않는다.
- 페이지 청크 요청 중 연결 실패 → 안내 → 재시도 성공. PC→모바일 폭 변경, 오프라인 페이지 이동 후 재연결·재시도 정상.

## 실제 응답·이미지 표본

서버 내부에서 공개 개발 도메인으로 호출한 시간이며 외부 사용자 왕복 지연은 포함하지 않는다.

| API | 3회 응답시간(ms) | 응답 크기 |
| --- | --- | --- |
| 영상 variety 24개 | 53.2 / 24.4 / 14.7 | 9,679bytes |
| 2026년 9월 일정 | 32.8 / 14.4 / 14.4 | 34,155bytes |
| 일정 검색 워크돌 | 47.1 / 26.6 / 26.1 | 6,415bytes |
| 홈 앨범 hero | 15.4 / 14.9 / 13.0 | 3,421bytes |

모두 HTTP 200. 홈 사진 표본 3개는 medium_800 WebP, 약 108~210KB. 파일 HEAD에는 Cache-Control이 없었으며 이번 작업에서 공유 저장소 정책은 바꾸지 않았다. 웹 JS/CSS의 기존 30일 immutable 캐시는 유지한다. 원본 사진 전체를 첫 화면에 내려받는 방식은 아니다.
